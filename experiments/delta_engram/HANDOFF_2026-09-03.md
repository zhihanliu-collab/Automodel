## 4. Delta architecture implemented in this branch

The original Base Engram and Base PLE remain untouched. Decoder index 1 (the
published Layer-2 PLE insertion point) computes both branches from the same
pre-injection HyperConnection state:

```text
ple_input = hidden_states
hidden_states += base_ple(ple_input, input_ids)       # frozen
hidden_states += delta_ple(ple_input, input_ids)      # additive/trainable branch
```

Delta details:

- 8 raw-token bigram heads and 8 raw-token trigram heads;
- 160 dimensions per head, concatenated to the unchanged 2560-dimensional PLE
  interface;
- nominal 1,000,000 rows/head; each head uses a distinct prime modulus from
  1,000,003 through 1,000,199;
- total padded rows `16,001,920`;
- table parameters `16,001,920 x 160 = 2,560,307,200`;
- Delta-PLE K/V trainable parameters `32,768,000` (`26,214,400` key and
  `6,553,600` value);
- total trainable parameters `2,593,075,200`, 1.44% of the
  `179,537,046,400`-parameter instantiated model;
- Delta hash multipliers are independent from Base and are
  `6364136223846793005`, `1442695040888963407`, and
  `3202034522624059733`;
- tokenizer, EOS/reset semantics, head count, feature width, PLE reader shape,
  and insertion layer match Base.

Initialization is function-preserving: the complete Delta reader is copied
from Base PLE, then the Delta table is set to exact zero. Therefore initial
Delta output is zero, while the copied nonzero value projection gives touched
table rows a nonzero first-step gradient. Training unfreezes only:

```text
*.delta_ple.ple_embedding.ngram_embedding
*.delta_ple.key_proj
*.delta_ple.value_proj
```

Primary implementation files:

- `nemo_automodel/components/models/qwen3_8_flash_next/config.py`
- `nemo_automodel/components/models/qwen3_8_flash_next/engram.py`
- `nemo_automodel/components/models/qwen3_8_flash_next/layers.py`
- `nemo_automodel/components/models/qwen3_8_flash_next/model.py`
- `nemo_automodel/components/models/qwen3_8_flash_next/state_dict_adapter.py`

The owner-sharded Base and Delta tables use autograd-aware All-to-All routing.
They remain model-owned sharded parameters under FSDP2 rather than being wrapped
a second time.

## 6. Hash/row-utilization result

The formal train split has:

```text
shifted train tokens: 68,534,256
unique raw bigrams:      354,762
unique raw trigrams:   1,272,643
```

For the eight bigram heads, occupied hashed rows range from 298,464 to 298,999
per approximately one-million-row head. For the eight trigram heads they range
from 719,619 to 720,236. Every head's actual/expected uniform occupancy ratio is
within about 0.1% of 1.0. This rules out a pathological hash distribution.

At step 329, the overall table nonzero fraction is `0.5091633`, which matches
the mean of expected bigram/trigram occupancy. The zero rows are therefore
primarily untouched capacity, not evidence that touched rows failed to receive
updates. Current evidence favors a table-capacity/data-allocation question over
a hash implementation bug. A later data-aware exact-hot plus hashed-tail design
is still a worthwhile ablation, but it is not required to interpret this run.

### 7.1 Steps and batching

- 1,321 train records; StatefulDataLoader uses length grouping and shuffle.
- Effective DP is 4, so one unaligned tail sample is not consumed per epoch.
- 1,320 consumed samples/epoch / global batch 4 = 330 optimizer steps/epoch.
- Four epochs = 1,320 optimizer steps total.
- Local batch is 1 and global batch is 4; there is no gradient accumulation.
- Context limit 131,072; collator pads to a multiple of 1,024.
- CP8 distributes each sample over eight ranks.
- Activation checkpointing is enabled except for the PLE-containing decoder
  block, whose owner-sharded lookup has collective side effects.

### 7.3 Optimizer and scheduler

Optimizer: Transformer Engine `FusedAdam` with FP32 master weights and FP32
first/second moments.

```text
betas = (0.9, 0.95)
eps = 1e-8
weight decay = 0
Delta-PLE K/V peak LR = 3e-6
Delta table peak LR = 3e-5 (10x group multiplier)
warmup = 13 optimizer steps, beginning at 10% of peak
decay = cosine through step 1320
terminal K/V LR = 3e-7
terminal table LR = 3e-6
global L2 gradient clip = 1.0
```

Logged `grad_norm` is the pre-clipping global norm. The actual update is clipped
to 1.0 using the FSDP/DTensor-aware path and only trainable parameters. Through
step 479, all 480 logged norms exceeded 1.0; median was about 3.13, p90 about
22.93, and 19% exceeded 10. This was observed, not a request to change the clip.

The W&B `overfit/train_loss_ema` uses decay 0.9 over logged per-step loss:

```text
ema_t = 0.9 * ema_(t-1) + 0.1 * loss_t
```

It is only a smoothed visualization, not another loss term and not the optimizer
objective.

## 11. Unresolved FlexAttention fallback/OOM

### 11.1 Failure signature

The sparse QSA wrapper compiles PyTorch FlexAttention. After enough graph
variants, Dynamo stops compiling and silently calls eager FlexAttention:

```text
UserWarning: flex_attention called without torch.compile() - this will use an
unfused implementation that materializes the full scores matrix
```

The eager path then allocates a dense score tensor and OOMs. Job 4796 attempted
about 48.94 GiB per affected rank; job 4800 attempted about 51.19 GiB. This is
not a model-weight or Delta-table OOM.

Runtime Torch 2.10 values:

```text
recompile_limit = 8
accumulated_recompile_limit = 256
skip_code_recursive_on_cache_limit_hit = True
dynamic_shapes = True
automatic_dynamic_shapes = True
```

### 11.2 What was tried

Commit `f8da1cc72` changed the accumulated limit from 256 to at least 1024 while
keeping `torch.compile(flex_attention, dynamic=False)`. It moved the failure
from roughly step 241 to step 480 but did not solve it. Do not raise another
arbitrary finite limit and call the bug fixed.

Commit `55754dd27` removed that workaround and used
`torch.compile(flex_attention, dynamic=True)`. Its CPU construction test passed,
but B200 functional job 4828 set `error_on_recompile=True` and called three
CP-like shapes. The second length failed with:

```text
Recompiling function flex_attention ...
tensor 'block_mask.q_indices' size mismatch at index 3. expected 2, actual 3
```

Therefore symbolic Q/KV sequence dimensions alone do not stabilize all
`BlockMask` metadata tensor shapes. No 32-GPU formal job was launched from this
commit.

### 11.3 Required next investigation

The focused test is:

```text
tests/functional_tests/models/qwen3_8_flash_next/test_flex_qsa_compile_stability.py
```

Work in this order:

1. Add a same-length/multiple-mask case with `error_on_recompile=True` to
   separate data-dependent closure guards from geometry-dependent metadata.
2. Inspect all `BlockMask` tensor shapes across real CP8 batches, especially
   `q_indices`, `kv_indices`, and their full-block variants.
3. Test explicitly marking the varying BlockMask tensor axes dynamic before the
   compiled call. Require multi-length forward and backward with no recompile.
4. If FlexAttention specializes these metadata widths by design, normalize or
   pad the BlockMask metadata to a bounded shape, or cache a genuinely distinct
   compiled graph per stable geometry without exhausting the process-wide code
   limit. Preserve exact route-mask semantics and backward gradients.
5. Promote the eager-fallback warning to an error in the formal path so future
   failures stop before attempting a 50 GiB dense allocation.
6. Run the focused one-GPU B200 regression across many actual padded shapes and
   new membership tensors. It must pass forward/backward with zero eager
   fallback.
7. Resume the 32-GPU run from step 329. It must cross the former step-480
   failure and successfully validate/save step 494 before declaring the fix.

Coarsening the 1,024-token padding buckets may reduce geometry variants but
must not be assumed to solve per-batch closure/metadata specialization. Measure
padding overhead and compile counts if it is used as part of the fix.
